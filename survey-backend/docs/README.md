# Survey Management System --- Backend Documentation

## 1. Overview

The backend provides the REST API and application logic for the Survey
Management System. It is built with **Java 21**, **Spring Boot**,
**Spring Data JPA/Hibernate**, and **SQLite**.

The backend supports the survey lifecycle:

1.  An administrator creates a survey.
2.  The administrator edits and publishes it.
3.  Respondents retrieve the published survey and submit answers.
4.  The administrator views submitted responses and survey analytics.
5.  The administrator closes the survey.
6.  After closure, the administrator can export the survey responses as
    a CSV file.

> This project currently implements the survey and response workflows.
> Authentication and role-based authorization have not been added, so
> the `/api/admin/**` routes should not be considered access-controlled
> in a production deployment.

## 3. Project Configuration

The backend application is configured to run on port `5454`.

Example `application.properties` settings:

``` properties
spring.application.name=survey-backend
server.port=5454

spring.datasource.url=jdbc:sqlite:mydb.db
spring.jpa.database-platform=org.hibernate.community.dialect.SQLiteDialect
spring.jpa.hibernate.ddl-auto=update
```

The SQLite database file is named `mydb.db`.

The frontend communicates with the backend using:

``` text
http://localhost:5454/api
```

The backend CORS configuration must allow the frontend development
origin (currently `http://localhost:5174`).

## 4. Main Backend Structure

The application uses a layered structure:

``` text
com.survey
├── controller
│   └── REST API endpoints
├── dto
│   ├── request
│   └── response
├── entity
│   ├── Survey
│   ├── SurveyResponse
│   └── enums
├── repo
│   ├── SurveyRepo
│   └── SurveyResponseRepo
└── service
    ├── SurveyService
    ├── ResponseService
    ├── JsonService
    └── ResponseAnswerValidator
```

The exact project may contain additional DTOs, validators, configuration
classes, and services.

### Layer responsibilities

-   **Controller:** receives HTTP requests, validates request bodies,
    calls services, and returns HTTP responses.
-   **Service:** contains business rules and coordinates repository and
    validation operations.
-   **Repository:** performs database operations through Spring Data
    JPA.
-   **Entity:** represents persisted database records.
-   **DTO:** defines the data accepted by or returned from API
    operations.
-   **Validator:** checks submitted answers against the survey's
    question schema.
-   **JsonService:** reads and writes JSON stored in database text
    columns.

## 5. Data Model

The application uses two main entities: `Survey` and `SurveyResponse`.

### 5.1 Survey

The `Survey` entity represents a survey definition.

  Field              Description
  ------------------ ----------------------------------------------
  `id`               UUID primary key generated by Hibernate
  `title`            Survey title
  `description`      Survey description
  `status`           Survey lifecycle status
  `currentVersion`   Current version field retained in the entity
  `createdAt`        Creation timestamp
  `updatedAt`        Last update timestamp
  `schemaJson`       JSON text describing the survey questions

Survey statuses:

-   `DRAFT` --- survey is being prepared.
-   `PUBLISHED` --- survey is available for public responses.
-   `CLOSED` --- new responses are no longer accepted and CSV export is
    allowed.

The entity provides operations to update survey details, publish a
survey, and close a survey. JPA lifecycle callbacks populate and update
timestamps.

### 5.2 SurveyResponse

The `SurveyResponse` entity represents one respondent's submission.

  Field           Description
  --------------- ---------------------------------------------------
  `id`            String containing a generated UUID
  `survey`        Many-to-one relationship to the associated survey
  `answersJson`   Submitted answers stored as JSON text
  `submittedAt`   Submission timestamp

Each response belongs to one survey. The `survey_id` column is indexed
to support response lookups.

The submitted answers are stored as JSON in SQLite rather than creating
a separate database column for every question.

### 5.3 Relationship

``` text
Survey (1) ──────────── (*) SurveyResponse
```

One survey can have many responses. Each response belongs to exactly one
survey.

## 6. Survey Question Schema

A survey's question definition is stored in `Survey.schemaJson`.

The frontend and backend use a JSON schema containing a `questions`
array. Each question includes fields such as:

-   `id`
-   `title`
-   `type`
-   `required`
-   `order`
-   `options`
-   optional `condition`

Supported question types:

  Type              Purpose
  ----------------- -------------------------
  `TEXT`            Free-text answer
  `SINGLE_CHOICE`   Select one option
  `MULTI_SELECT`    Select multiple options
  `RATING`          Numeric rating

Conditional question metadata supports `EQUALS` and `NOT_EQUALS`
operators in the current model. Conditional display behaviour should be
documented as implemented only after it has been completed and tested in
the application.

### 7.3 Response submission workflow

When a respondent submits a survey:

1.  `ResponseController` receives the survey UUID and request body.
2.  `ResponseService` retrieves the survey using the published-survey
    lookup.
3.  `JsonService` reads the survey question schema.
4.  `ResponseAnswerValidator` validates the submitted answers against
    the schema.
5.  The answers are serialized to JSON.
6.  A `SurveyResponse` entity is created and saved.
7.  A response DTO is returned to the client.

The public submission flow accepts responses only for published surveys.

## 8. Survey Analytics

The analytics endpoint is:

``` http
GET /api/admin/surveys/{id}/analytics
```

The analytics response is designed to provide:

-   Total number of responses.
-   Per-question answered count.
-   Option counts for single-choice and multi-select questions.
-   Average rating for rating questions.
-   Text answers for free-text questions.

The frontend uses these values to render survey statistics and
question-level summaries.

## 9. CSV Response Export

The CSV export endpoint is:

``` http
GET /api/admin/surveys/{surveyId}/responses/export
```

### Export rules

-   The survey must exist.
-   The survey status must be `CLOSED`.
-   Draft and published surveys cannot be exported.
-   Every question is represented by a CSV column.
-   Every submitted response is represented by one row.
-   The first column contains the submission timestamp.
-   Multi-select answers are combined into one cell, separated by
    semicolons.
-   CSV values are quoted and embedded quotation marks are escaped.
-   The response is encoded as UTF-8, with a UTF-8 BOM to improve
    compatibility with spreadsheet software.

If the survey is not closed, the service returns HTTP `409 Conflict`.

The controller returns the CSV bytes with a downloadable attachment
filename similar to:

``` text
survey-responses-<survey-uuid>.csv
```

### Example CSV layout

``` csv
"Submitted At","Name","How satisfied are you?","Additional feedback"
"2026-11-18T10:30:00","Alex","5","Very helpful"
"2026-11-18T11:15:00","Sam","4","Good experience"
```

The actual columns are generated from the survey's question schema.

## 10. Important Implementation Details

-   Survey IDs are UUIDs.
-   Response IDs are strings containing UUID values.
-   The response repository therefore uses
    `JpaRepository<SurveyResponse, String>`, while its survey
    relationship query methods accept a `UUID`.
-   Answers and survey question schemas are stored as JSON text.
-   Response retrieval is ordered by submission time, newest first.
-   Survey deletion should remove associated responses before deleting
    the survey if database cascade behaviour is not configured.
-   The response controller currently returns response entities from the
    administrator response-list endpoint. For a production API,
    returning response DTOs is preferable to exposing JPA entities
    directly.

## 13. Current Scope and Future Considerations

The implemented scope covers survey creation and management, public
response submission, response retrieval, analytics, and CSV export after
closure.

The following are not currently part of the implemented scope:

-   Authentication and role-based access control.
-   Rate limiting and spam protection.
-   Partial response saving.
-   Survey version history.
-   Production deployment configuration.

Before exposing the application publicly, add appropriate authentication
and authorization, secure the administrator endpoints, configure
production database backups, and review input validation and operational
security.
